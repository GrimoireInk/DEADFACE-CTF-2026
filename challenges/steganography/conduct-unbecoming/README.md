## 2. Technical Concepts

### 2.1 Steganography

Steganography is the practice of concealing information inside another medium.

Digital images are common carriers because they contain large amounts of visual data and can conceal subtle modifications.

Potential hiding locations include:

- Image metadata
- Individual color channels
- Pixel intensity variations
- Embedded files
- Appended data
- Low-contrast visual patterns

In this challenge, the concealed information was represented as a faint dot matrix placed in an otherwise ordinary document image.

### 2.2 JPEG Metadata

JPEG files can contain several metadata structures, including:

- EXIF
- XMP
- IPTC
- Photoshop image resource blocks
- ICC color profiles

These structures may contain information about image creation, editing software, timestamps, and identifiers.

ExifTool was used to examine these fields.

### 2.3 Image Enhancement

Image enhancement can reveal visual information that is difficult to distinguish in the original image.

Useful methods include:

- Color-channel separation
- Contrast enhancement
- Color inversion
- Autocontrast
- Cropping and enlargement

These techniques helped isolate the hidden dot pattern.

### 2.4 Binary-to-ASCII Encoding

ASCII characters can be represented using eight-bit binary values.

For example:

| Character | Binary | Decimal |
|---|---|---|
| N | `01001110` | 78 |
| V | `01010110` | 86 |
| U | `01010101` | 85 |
| - | `00101101` | 45 |

A visual dot matrix can represent these bits, using occupied and empty positions.

The correct interpretation must be established by observing the pattern and testing whether the resulting values produce coherent text.

## 3. Investigation Methodology

### Evidence Acquisition

The challenge supplied an image representing an internal university document.

Initially, the evidence was saved as:

```text
Conduct Unbecoming.pdf
```

The PDF was generated by Safari rather than being the original challenge artifact.

This was evident from its metadata:

```text
Creator  : Safari
Producer : macOS Quartz PDFContext
Title    : Doc_20261017_0915.jpg 2,566×3,314 pixels
```

Because conversion to PDF can change the original file structure and metadata, the original JPEG was subsequently acquired.

```text
Doc_20261017_0915.jpg
```

The JPEG became the primary forensic evidence.

### Identify the Original File

The image was examined using:

```bash
file "Doc_20261017_0915.jpg"
```

The file was identified as JPEG.

ExifTool confirmed:

```text
FileType       : JPEG
MIMEType       : image/jpeg
ImageWidth     : 2566
ImageHeight    : 3314
FileSize       : 3.5 MB
```

The JPEG contained a full-page university conduct notice.

### Examine EXIF, XMP, and IPTC Metadata

The following command was used:

```bash
exiftool -a -u -G1 -s "Doc_20261017_0915.jpg"
```

Notable results included:

```text
ObjectName            : NVU Conduct Notice
ModifyDate            : 2026:06:08 17:48:35
XMPToolkit            : XMP Core 5.5.0
HistoryAction         : produced
HistorySoftwareAgent  : Affinity Photo 2 2.6.5
HistoryWhen           : 2026:06:08 17:48:35-04:00
```

These fields established that the JPEG had been processed using Affinity Photo 2.

However, no explicit asset ID was recovered.

### Search for Embedded Identifiers

The file was searched for readable strings:

```bash
strings -a "Doc_20261017_0915.jpg" \
  | grep -iE 'asset|id|uuid|nvu|conduct'
```

The search returned XMP metadata and numerous incidental matches from compressed image data.

No confirmed asset identifier was found.

The XMP packet was also extracted directly:

```bash
exiftool -b -XMP "Doc_20261017_0915.jpg" \
  | grep -iE 'asset|document|instance|uuid|resource|source|id='
```

This confirmed the previously identified metadata without revealing the requested asset ID.

### Inspect the Document Visually

The document was opened using:

Although the student and document identifiers were visible, neither was specifically identified as the asset ID used to create the document.

### Check for Appended Data

A Python script examined the JPEG's final end-of-image marker.

```python
from pathlib import Path

path = Path("Doc_20261017_0915.jpg")
data = path.read_bytes()

end = data.rfind(b"\xff\xd9")
trailing = data[end + 2:] if end != -1 else b""

print(f"File size: {len(data):,} bytes")
print(f"Last JPEG end marker offset: {end}")
print(f"Bytes after JPEG end marker: {len(trailing):,}")
```

The output was:

```text
File size: 3,485,248 bytes
Last JPEG end marker offset: 3485246
Bytes after JPEG end marker: 0
```

No data was present after the final JPEG marker.

This ruled out a simple appended-payload technique.

### Inspect JPEG Application Segments

ExifTool's verbose mode was used:

```bash
exiftool -v3 "Doc_20261017_0915.jpg" > jpeg_structure.txt
```

Relevant structures were located using:

```bash
grep -inE 'APP[0-9]+|8BIM|XMP|IPTC|COM|unknown|trailer' \
  jpeg_structure.txt | head -80
```

The image contained standard JPEG application segments:

| Segment | Contents |
|---|---|
| APP0 | JFIF |
| APP13 | Photoshop/IPTC |
| APP1 | EXIF |
| APP2 | ICC profile |
| APP1 | XMP |

No obvious anomalous segment was identified.

### Generate Enhanced Images

With no asset ID recovered from metadata or file structure, attention shifted toward the image pixels.

A Python script was created:

```text
analyze_conduct.py
```

The script used Pillow to separate image color channels, invert the image, and enhance contrast.

```python
from PIL import Image, ImageOps, ImageEnhance

image = Image.open("Doc_20261017_0915.jpg").convert("RGB")

for channel, name in zip(
    image.split(),
    ["red", "green", "blue"]
):
    enhanced = ImageOps.autocontrast(channel)
    enhanced.save(f"conduct_{name}_channel.png")

inverted = ImageOps.invert(image)
inverted.save("conduct_inverted.png")

contrast = ImageEnhance.Contrast(image).enhance(4)
contrast.save("conduct_high_contrast.png")

print("Created five analysis images.")
```

The script was executed:

```bash
python3 analyze_conduct.py
```

Output:

```text
Created five analysis images.
```

The images were opened:

```bash
open conduct_*.png
```

### Discover the Hidden Dot Pattern

During visual analysis, faint dots were observed near the bottom-right corner of the document, close to the page-number text.

The dots were particularly noticeable in the enhanced blue-channel image.

Unlike the surrounding document content, they formed a structured arrangement of repeated vertical and horizontal positions.

This suggested that the marks might represent encoded data rather than ordinary rendering noise.

### Enlarge the Suspicious Region

A second Pillow script isolated the lower-right portion of the blue-channel image.

```python
from PIL import Image, ImageEnhance, ImageOps

img = Image.open("conduct_blue_channel.png").convert("L")
w, h = img.size

crop = img.crop((
    int(w * 0.75),
    int(h * 0.80),
    w,
    h
))

crop = crop.resize(
    (crop.width * 4, crop.height * 4),
    Image.Resampling.NEAREST
)

crop = ImageOps.autocontrast(crop)
crop = ImageEnhance.Contrast(crop).enhance(3)

crop.save("conduct_corner_analysis.png")

print("Saved conduct_corner_analysis.png")
```

The enlarged output made the dot positions substantially easier to distinguish.

```text
conduct_corner_analysis.png
```

The pattern was arranged into a grid of eight possible positions per row.

### Recover the Encoded Asset Identifier

The dot matrix was interpreted as a sequence of eight-bit binary values.

Under this interpretation:

- A dot represented `1`.
- An empty position represented `0`.
- Each row represented one byte.
- Each byte could be converted into its corresponding ASCII character.

The decoded message consisted of a marker byte followed by an asset identifier.

| Row | Binary | ASCII |
|---|---|---|
| 1 | `11111111` | Marker (`0xFF`) |
| 2 | `01001110` | N |
| 3 | `01010110` | V |
| 4 | `01010101` | U |
| 5 | `00101101` | - |
| 6 | `01010000` | P |
| 7 | `01010010` | R |
| 8 | `01001001` | I |
| 9 | `01001110` | N |
| 10 | `01010100` | T |
| 11 | `00101101` | - |
| 12 | `00110001` | 1 |
| 13 | `00110111` | 7 |

Excluding the initial marker produced:

```text
NVU-PRINT-17
```

This identifier matched the type of asset ID requested by the challenge.

**Recovered asset ID:**

`NVU-PRINT-17`

### Verify the Decoded Flag

The recovered asset identifier was placed inside the required flag format:

```text
deadface{NVU-PRINT-17}
```

This was confirmed as the correct challenge flag during the post-CTF investigation.
